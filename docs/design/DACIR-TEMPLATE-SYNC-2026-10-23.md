# Nodu 模板自动同步设计

日期：2026-10-23。状态：设计方案，尚未实现客户端自动同步。本次仅核对现有代码并制定方案，不修改产品界面、不发布新版模板。

目标：独立仓库发布经过验证的稳定模板后，Nodu 可自动获得更新；无需等待 Nodu 重新发版。搭芯仍是独立应用，模板只出现在现有“新建项目”的模板选项中。已有工程不参与自动同步。

## 当前基础与缺口

- 仓库：`https://github.com/libai1024/dacir-templates`。
- 初始标签 `v0.1.0`，Git 提交 `3ccb83d143175c5085b87c6bb553b3fd669cea83`。
- 包内容摘要 `1e24a8feb72827e2414245aa6b98eee006ccd401c5f6340cd236a1f685cfe9bf`，包版本 `snapshot-1e24a8feb72827e2`。
- 当前只有 Git 标签，尚未创建带分发资产的 GitHub Release。
- `sync-daxin-templates.cjs` 仍读取开发者本机搭芯目录，不访问独立 Git 仓库。
- `createDaxinProject` 已接受模板根目录参数，检查文件摘要、文件大小和路径，生成 `template-origin.json` 与 `nodu.lock.json`。
- `nodu-embedded-server.ts` 仍固定传入 `resources/daxin`；目录和模板选项是静态白名单，尚无缓存解析器、更新调度、兼容性清单或激活记录。
- 现有项目创建流程会尝试自动登记为可信项目。新同步包含 CMake 和运行时源码，不能仅凭下载成功或自带摘要就继承这种信任。

## 推荐的同步链路

```text
维护者提交到 dacir-templates
    ↓
CI 校验清单并真实编译三个模板
    ↓
发布不可移动的版本标签和 Release 模板包
    ↓
将已测试版本加入签名的 stable 版本清单
    ↓
Nodu 后台检查兼容版本
    ↓
下载临时包、验证来源、验证内容和结构
    ↓
保存不可变缓存并切换当前版本
    ↓
下一次打开“新建项目”使用新版本
```

Git 管理源码和版本；Nodu 用户端通过 HTTPS 获取由该 Git 提交生成的发布包，不要求用户安装 Git、登录 GitHub 或提供访问令牌。维护者及 Nodu 打包流程仍用 Git 按明确提交同步。客户端不在用户项目目录执行 Git 命令。

比较：只在 Nodu 打包时同步 Git 最简单，但模板更新必须等待应用升级；客户端追踪 main 会把普通提交直接变成用户模板；稳定发布包缓存同时满足独立更新、离线使用和版本可追溯，采用此方案。

## 发布协议

保留现有 `manifest.json` 的内容摘要协议，避免覆盖或移动已发布的 `v0.1.0`。增加独立的分发清单及签名，不将后续发布信息倒填到旧 Git 提交。

1. 标签选择明确的语义版本。只包含清单白名单中的 `templates/`、`support/`、`adapter/`、`licenses/` 与 `manifest.json`；不包含 Git 历史、用户工程、开发证据、node_modules 或构建产物。
2. 发行资产包括模板压缩包与校验数据。构建发布资产后按其实际字节计算 SHA-256；不能把包内容摘要误当压缩包摘要。
3. 小型 `stable.json` 索引包含：单调递增 revision、有效期、发行记录数组。每条记录包含 version、完整 Git commit、下载地址、archiveSha256、contentSha256、manifestSchema、generatorApi、adapterApi、最低/最高 Nodu 版本、平台条件、目标芯片白名单、SDK/toolchain 约束、withdrawn 状态。
4. 索引保留多个仍受支持的稳定版本，客户端选择自己兼容的最高版本。不能只查一个 latest 版本后因为不兼容而漏掉可用旧版本；不根据日期字符串排序版本。
5. 使用独立发布密钥签名索引；Nodu 内置公钥，验签通过后才信任索引中的提交和包摘要。模板包不能自行提供新的信任公钥。签名密钥存于受保护发布环境，后续轮换由受信任应用更新或旧钥签署的轮换协议处理。
6. 同一版本、提交和摘要一经发布不改变；修复使用新版本。标签名只用于展示，完整提交与摘要用于锁定实际内容。稳定索引可以撤回问题版本，但不能修改已发布资产冒充原版。
7. 发布前执行清单/语法检查和三个模板实际编译，并审核 CMake/支持文件变更。签名证明发布来源，不代替功能测试。

GitHub Release 提供 draft、prerelease、tag_name 和 assets 等字段，可以承载发布包；客户端仍以受信任的 stable 索引确定可用版本，不能只凭 release 标题或 latest 接口决定。
来源：[GitHub Releases API](https://docs.github.com/en/rest/releases/releases)。

当前 `v0.1.0` 可作为第一份内置基线：按已验证的 commit/contentSha 固定；只有补齐发行资产与签名发布流程后，才开启未来版本的自动激活。不能将现有普通标签当作已验签的发行版本。

## 客户端时机与界面

- 启动完成后延迟约 15 秒执行后台检查；后台保持运行时每 24 小时检查一次，带少量随机抖动，避免集中请求。记录上次检查时间，重启不重复高频请求。
- 打开“新建项目”时，立即读取已验证的本地版本；若检查已到期，在后台发起检查，窗口不等待网络。
- 当前已打开的创建窗口固定模板包 ID。即使后台更新完成，当前选择与创建操作仍使用该包；下一次打开窗口才使用新包。
- 保留现有模板名称，不拼接版本号、状态解释或“·”文案。不增加搭芯主页、侧栏、常驻状态、提示弹窗。
- 可在现有应用设置中增加一个“自动更新项目模板”开关和“检查更新”操作；版本及失败详情仅在此处或开发日志中显示。它们属于通用模板设置，不新增搭芯顶级入口。默认开启；用户关闭后停止后台网络请求，内置模板和缓存仍可用。
- 自动更新成功静默生效。离线、限流、签名不符等情况下保留可用版本，后台失败不弹窗；用户主动检查时才显示简短结果。
- 支持 ETag / If-None-Match，304 表示无需重新下载；遵守 Retry-After 和服务端限流头，网络失败退避，不无限重试。匿名请求不假定享有认证请求的额度豁免。
来源：[GitHub REST 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)。

## 安装、校验和并发

建议缓存放在 Nodu 用户数据目录，不写应用安装目录：

```text
templates/dacir/
├── packs/<contentSha256>/    # 校验完毕后不可变
├── staging/<operationId>/   # 尚未激活的下载/解包
├── active.json              # 当前包、上一包及来源
├── update-state.json        # ETag、检查时间、失败退避、最高索引 revision
└── install.lock             # 同一用户配置的安装互斥
```

内置模板继续位于 `resources/daxin`，用于首次离线使用和最终回退。

校验顺序：

1. 验证索引签名、revision 和有效期；过期索引不激活新包，已验证缓存仍可使用。
2. 匹配 Nodu/generator/adapter/芯片/SDK/toolchain 条件，第一版只开放现有三种 F103C8T6 模板；未知模板或芯片不能靠远程清单绕过本地白名单。
3. 下载到 staging，限制超时、压缩包大小和流量；初始建议压缩包不超过 16 MiB、解包总量 32 MiB、单文件 4 MiB、最多 4096 个文件。索引本身限制 256 KiB。
4. 验证压缩包 SHA，再解包。拒绝路径穿越、绝对路径、符号链接、硬链接、特殊设备、Windows 保留名、大小写冲突、重复文件和压缩炸弹。仅接受固定 HTTPS 发布来源及必要的 GitHub 下载重定向域，不提供任意仓库 URL 输入。
5. 独立校验 manifest 的 schema/provider、模板清单、完整文件集合、逐文件摘要与内容摘要；校验索引 commit 与分发信息一致。哈希列表按已约定的排序与 UTF-8 序列化规则计算，拒绝重复 JSON 键和格式歧义。
6. 校验器使用 Nodu 自带实现；不运行下载仓库中的脚本，不执行 npm install、Git hook、submodule、编译、烧录或串口操作。CMake 文件仅在用户随后正常触发项目构建时使用。
7. 校验完成后将临时目录移动到以内容摘要命名的最终目录，再通过同文件系统临时文件替换激活指针。激活前所有步骤失败都不影响旧版本。
8. 跨进程安装锁防止多个窗口重复安装；创建工程持有包 ID 的读引用。清理只处理没有读引用的缓存，绝不删除创建中的模板。
9. 启动恢复时丢弃不完整 staging；若 active 不存在、损坏或校验失败，尝试 previous，再使用内置包。保留最近两个已验证版本，限制缓存上限；现有项目有独立副本，不依赖缓存存活。

安装完成不在每台用户电脑后台自动编译模板。正确性以发布验证为前提；本地完整性故障可自动回退，真实编译问题不能一概归因为模板并偷偷降级。

## 版本撤回与已有工程

- 发布者在签名索引中撤回问题版本，下一次检查后停止将其用于新建项目，切换至兼容的未撤回版本或内置基线。回退属于明确的撤回处理，普通更新不接受版本倒退。
- 已打开的创建窗口若绑定版本被撤回，在点击创建时阻止继续使用该版本，给出一次简短错误并要求重新选择；不能静默改用不同文件创建。
- 已有工程不改名、不覆盖、不自动切换驱动、接线、环境、CMake 或配置，不对其执行 pull/merge。
- 创建时扩充 `template-origin.json` 与 `nodu.lock.json`：repository、releaseVersion、完整 commit、contentSha256、manifestSchema、adapterApi、templateId、逐文件基线摘要。原有旧项目锁不强行重写。
- “模板库已更新”与“我的工程升级”是两件事。本期只实现前者；需要升级旧工程时，用新模板创建独立工程并比较迁入。三方合并不放进本期自动更新。

## 代码落点与实施顺序

1. **先完成固定 Git 版本接入**：新增 `desktop/dacir-templates.lock.json`，固定当前 v0.1.0/完整 commit/contentSha；将发布打包同步命令改为从独立仓库按锁提取。旧本机源码导出脚本改成显式维护工具，避免日常同步将通用命名版覆盖回旧版。发布构建默认只读锁，不自动追踪 main。
2. **发布端补齐稳定分发**：在模板仓库新增发布工作流、兼容性元数据、受保护签名与 stable 索引；建立不可变标签/资产规则。模板更新可独立发布，不要求更新 Nodu 版本锁；版本锁只固定每版 Nodu 的离线基线。
3. **客户端模板服务**：新增后端 `TemplateRegistryService`，负责版本发现、兼容筛选、下载、验证、缓存、激活和撤回。拆分可测试的 verifier/cache/resolver，复用现有校验但不能让下载脚本充当可信校验器。
4. **接入创建流程**：模板列表返回 packId；创建 RPC 携带 packId，服务端从登记表解析路径，不能接受前端任意文件路径。`createDaxinProject` 继续接收已验证根目录。自动信任只适用于内置或验签通过的发行包。
5. **最小设置与测试**：接入现有设置中的自动更新/主动检查；界面原有模板位置不变。回归通过后打包发布 Nodu，用户从这一版本开始具备后台同步能力。

这五步共同构成完整自动同步，第一步做完只能称为“发布时 Git 同步”，不能称为“用户端已自动更新”。第一版暂不提供自定义 Git 仓库、测试版渠道、实时 main 分支跟踪或旧工程自动合并。

## 验收矩阵

- 首次离线：三套内置模板均可创建、编译。
- 稳定版本升级：下载一次、校验一次；下次新建得到新版本，原工程全部文件与锁不变。
- 当前窗口冻结：后台更新不改变当前创建结果；下一窗口使用新包。
- 兼容性：跳过不兼容最新版本并选择仍可用的兼容版本；未知芯片、schema、adapter 拒绝。
- 信任：错误签名、改动的标签/提交/摘要、索引回放、错误芯片和被撤回版本不得自动激活。
- 文件安全：缺失/额外文件、损坏压缩包、路径穿越、重复条目、大小写冲突、软硬链接、超限均拒绝，原包可用。
- 网络：超时、离线、404、429、5xx、304 均不阻塞创建；退避与 ETag 行为可测。
- 中断与并发：下载中退出、激活中退出、两窗口同时更新、创建期间清理缓存均能恢复到一致状态。
- 回退：active 损坏回退 previous；两者不可用回退内置；不会覆盖用户工程。
- 更新过程硬件调用为零；模板真实编译、Windows/macOS 路径和锁行为分别验证。
- 首个在线版本从当前 GitHub 标签真实下载验证，记录来源提交、文件摘要与三个项目编译结果；不把测试服务器模拟结果当作真实发布验收。
