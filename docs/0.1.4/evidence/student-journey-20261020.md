## 已定位问题与修复边界

### 停止/断开中断 IDE 帧接收

`stop`/`disconnect` 入队会增加 cancellation generation；原来的空闲轮询
在帧 payload 尚未读完时检查该 generation，产生取消。底层正确地将残缺
事务判为 desync 并关端口，用户看到的是“停止”导致连接异常。

原版 `openmvpluginio.cpp@af179e44` 将停止命令排入队列，帧长度回复后把
frame-dump 放在后续命令之前；当前事务完成后才继续。

修复仅让有界的 IDE 空闲轮询先完成事务，再处理排队的停止/断开；
关闭输入、截止时间、传输失败仍 fail-closed。长耗时用户请求的取消策略、
固件门禁和低层协议解析没有放宽。

主机回归：两项注入“读到第一个帧字节时提交停止/断开”的测试从失败转为
通过；另有截断回复测试保证仍关闭故障连接。设备集成测试 33/33、
IDE 协议测试最终 22/22。最终 Rust 全工作区测试及 clippy `-D warnings`
通过，fmt、Node 后端 39/39、启动器语法检查、399 文件许可扫描及
`git diff --check` 通过。

### 补齐原版事务间隔后的真板复验

原版 `openmvpluginserialport.cpp` 每次串口事务结束后等待 macOS 2 ms /
其他平台 1 ms。Rust 已补齐成功读完整回复、成功写完整命令后的间隔；
未放宽短包和超时检查。

使用单一新日志订阅、明确的 UI 运行/停止按钮和实际帧序号采集：

| 冻结记录 | 结果 |
| --- | --- |
| `stop-fix-before-pacing.json` | 有新帧；停止时最终因只收到 3,228/3,236 字节而超时 |
| `stop-fix-after-pacing.json` | 自动化未真正点到连接，无运行记录；不能当作产品连接失败 |
| `stop-fix-after-pacing2.json` 第 1 次 | 10 秒采样帧号 1→96，停止 117 ms，保持连接，REPL `2` |
| 同上第 2 次 | 帧号 103→196，停止 229 ms，保持连接，REPL `2` |
| 同上第 3 次 | 帧号 202→294；随后只收到 1,906/1,936 字节而超时，连接关闭 |
| `recording-after-pacing.json` | 独立录像 45 帧/5,255 ms，正常收尾、停止与 REPL，通过一次 |

因此时序对齐和取消竞态修复有实际验证价值，但不能宣称“连续三次通过”
或“相机稳定性已经解决”。这些时间只描述本次操作，不是性能基准。

### 尚未解释的持续接收停滞

部分流在点击停止前已停止更新；自写色块 v1 的日志出现
`Device operation timed out`，不能把所有现象都归因于停止取消。
诊断记录包括 3,369/3,377、3,341/3,365、3,370/3,388，以及上述复验的
接收不足。它们只能证明主机未收到声明长度，不能证明丢失发生在尾部，
也不能单凭长度定位到固件、USB 桥或主机驱动。
录像请求可能排在阻塞的帧读取之后，又被随后停止取消；不能据此声称
录制动作本身损坏串口。下一步需要串口字节记录与可靠的原版同源复验。

### 排除不可靠自动化证据

- `s5/regress3-stream.json` 全部采样为无帧、未运行；虽有停止后 `2`，
  但不是“35 秒连续出图”或相机停止回归通过。
- 旧驱动重复添加日志监听，导致同一日志被记录两遍。不能由此推断脚本

  原始文件不修改，验收以可靠证据为准。

### 初学者体验缺口

- 烧写成功后连接是 raw，图像能力关闭、板名显示未识别；需手动重连 IDE
  才恢复预览和自动配置读取，界面缺少清晰的下一步。
- 相机适配与连接复位方式是两个选择项，野火板对应 Sipeed Maix Dock
  复位项时容易误解。
- 官方库原样收录，缺少面向当前板的硬件/引脚/helper 依赖提示。
- 备份证明保存在当前前端会话；页面重载后本地恢复包仍在，但不能直接
  继续烧写。不得通过忽略 session 门禁来“修复”这个体验问题。
- 进度条在不同阶段重置百分比，缺少阶段名称时容易理解为倒退。

后续状态以本文件及 [遗留问题](../remaining-work.md) 为准；旧的 USB 未枚举
记录只作为历史阻塞证据保留。
