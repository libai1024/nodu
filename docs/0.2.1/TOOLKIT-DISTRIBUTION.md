# Nodu 0.2.1 工具包分发设计

日期：2026-10-22。状态：**待评审，未实现。** 本文细化 [FUNCTIONAL-DESIGN §4](FUNCTIONAL-DESIGN.md#4-stm32-工具包)，回答评审中的三个问题：直接从官方站点下载是否可靠；能否放在 Nodu 自己的服务器上、登录后下载；能否在下载 Nodu 时就把对应平台的工具包打进安装包。

## 1. 结论

1. **按平台把 STM32 工具包打进 Nodu 安装包**（采纳评审提出的思路）。macOS 安装包带 macOS 版工具，Windows 安装包带 Windows 版工具。装好 Nodu 就能编译和下载，第一次使用不需要再下载任何东西，也不需要单独的安装步骤。
2. **实测代价可以接受。** 裁剪到 0.2.1 用得到的部分后，单架构的工具包安装后约 240 MB（macOS universal 约 390 MB）；按现有安装包的 zip 压缩，单架构安装包增加约 74 MB（macOS arm64 实测；其中 clangd 一项为估算，见 §3）。
3. **服务器仍然需要，但只托管 Nodu 安装包**和 GPL 组件的源码：国内对象存储加 CDN 为主，GitHub Releases 为备（§8）。安装包本来就要找地方放，所以没有增加新的运维工作。
4. **下载不需要登录（D8）。** 理由见 §9。
5. 运行时从服务器下载工具包（多节点、分块续传）不进 0.2.1。以后需要安装额外版本时再做（P1），设计保留在 §11。

## 2. 三种方案

| | A：直连官方站点 | B：自建服务器按需下载（可选登录） | C：打进安装包（推荐） |
| --- | --- | --- | --- |
| 第一次编译前是否要联网 | 要，从 6 个站点下载；仅 Arm 工具链（129 MB）和 clangd（95.4 MB）两项官方归档就超过 220 MB | 要，约 36 MB（tar.xz，§3） | 不要 |
| 断流的影响 | 任一站点慢或断开都装不上 | 靠多节点、分块续传缓解 | 只影响下载 Nodu 安装包本身 |
| 课堂 | 每台机器各下一遍 | 需要离线包或局域网共享 | 拷贝安装包即可 |
| 安装包体积 | 不变 | 不变 | macOS 单架构约 +74 MB；universal 约 +132 MB；Windows 待实测 |
| 服务器运维 | 无，但官方地址会变 | 存储、CDN、ICP 备案；要求登录时还要账号系统 | 存储、CDN、ICP 备案（托管安装包本来就需要） |
| 版本一致性 | 依赖官方长期保留旧文件 | 好 | 好，工具版本与应用版本绑定 |
| macOS 签名 | 下载的程序要单独处理隔离属性和签名 | 同左 | 与应用一起签名 |
| 只用 K210 的用户 | 不受影响 | 不受影响 | 多下载 74–132 MB 用不到的工具 |
| 升级工具 | 改清单即可 | 发新的组件包 | 随应用一起发布 |

方案 A 的问题来自上游本身，不只是网速：

| 组件 | 官方来源 | 问题 |
| --- | --- | --- |
| Arm GNU 工具链 | Arm 下载页 | 2026-10-22 访问时，下载页已 301 重定向到 `gitlab.arm.com/tooling/gnu-toolchains-for-arm`，Arm 称该项目现在是全部版本的正式发布位置。完整归档 129 MB（darwin-arm64），Nodu 只需要其中一小部分 |
| clangd | GitHub Releases | 23.1.0 的 mac 压缩包 95.4 MB、Windows 28.3 MB；GitHub 在国内的可用性不稳定 |
| CMake、Ninja | Kitware / GitHub | 同上 |
| OpenOCD | 上游只发布源码 | 没有官方的 Windows / macOS 二进制 |
| stm32flash | SourceForge | 0.7 只有源码包和一个未注明平台的 `binaries.zip`（231.8 kB） |
| HAL / CMSIS | ST 的 GitHub 仓库 | 要按 P0 锁定的三个 commit 稀疏检出并初始化子模块，不适合在学生电脑上做 |
| ST-LINK 驱动（Windows） | st.com | 据 ST 社区与 MathWorks 的说明，下载前要登录 my.ST 账号 |

国内访问上述站点的速度**本次没有实测**。即使速度没有问题，后几行也说明学生需要的东西，上游没有以现成的形式提供。B 和 C 都把这些处理放进 Nodu 的打包流水线，在 CI 里做一次；区别只在于产物是放上服务器，还是放进安装包。

## 3. 实测体积（macOS arm64）

2026-10-22 用 P0 机器上的文件实测。裁剪规则：

- 工具链只保留 C 前端（`cc1`）、binutils、GDB，以及 newlib / libgcc 的 `thumb/v7-m/nofp`（Cortex-M3）与 `thumb/v7e-m+fp/hard`（Cortex-M4F）两组多库、链接脚本和 specs。0.2.1 只支持 C，所以 C++ 标准库头文件（21 MB，约 1700 个文件）也去掉了。
- CMake 去掉帮助文档；SDK 只保留 HAL、CMSIS Core、F405 / F407 与 F103 的设备头文件和模板。

用裁剪后的工具链重新编译 P0 的两个目标，BIN 的 SHA-256 与 P0 记录的一致：F103C8 `fa7b5878…`（2624 B），F407ZG `8b97e496…`（3592 B）。

| 组件 | 安装后 | 文件数 | zip（deflate -9） | tar.xz -9 |
| --- | --- | --- | --- | --- |
| Arm GNU 14.2（只保留 C 与 M3 / M4F 多库） | 113.7 MB | 356 | 38.7 MB | 15.3 MB |
| CMake 4.4.3 | 24.6 MB | 1749 | 6.5 MB | 3.9 MB |
| Ninja 1.13.2 | 0.3 MB | 1 | 0.1 MB | 0.1 MB |
| OpenOCD 0.12.0 + scripts + 4 个依赖库 | 14.3 MB | 898 | 3.1 MB | 2.0 MB |
| stm32flash 0.7 | 0.1 MB | 1 | < 0.1 MB | < 0.1 MB |
| SDK：CubeF4 1.28.3 子集 | 16.8 MB | 350 | 2.3 MB | 0.9 MB |
| SDK：CubeF1 1.8.7 子集 | 8.8 MB | 243 | 1.3 MB | 0.6 MB |
| clangd（估算，见下） | 62.7 MB | 1 | 21.7 MB | 13.1 MB |
| **合计** | **238.4 MB** | **3599** | **73.8 MB** | **35.5 MB**（整体压缩） |

- 现有安装包用 zip（macOS 用 `ditto`，Windows 为便携 zip），所以安装包的增量按 deflate 一列计算。以后改用 DMG（LZMA）或 NSIS 安装程序时，增量会接近 tar.xz 一列；这一点没有实测。
- **clangd 是最大的不确定项。** 表中用 Xcode 自带的 clangd（Apple 构建，arm64）代替。官方 clangd 23.1.0 的 mac 压缩包有 95.4 MB，可能同时包含两种架构且没有剥离符号（未核实）。流水线会拆成单架构并剥离符号，M1 实测；如果超出预算，再考虑自行构建 clangd。
- OpenOCD 是 P0 用的 Homebrew 构建，只用于估算体积。正式版本从固定源码自行构建（§5.1）。
- 测量时去掉了 `share/doc` 等许可文件；正式打包必须加回，增加不到 1 MB。
- Windows 组件没有测量；Windows 版 GCC 是 `.exe` 加 MinGW 运行库，体积可能不同，M1 实测后补进本表。

## 4. 安装包里的布局

```
scope-extension/resources/toolkits/stm32/<platform>/        darwin 或 win32-x64
├── toolkit.json        工具包版本、组件版本、每个文件的大小与 SHA-256
├── arm-gnu/  cmake/  ninja/  openocd/  stm32flash/  clangd/
├── sdk/cube-f4/  sdk/cube-f1/
└── licenses/           各组件许可文件、GPL 源码的获取说明
```

- 与现有侧车（`resources/bin/<platform>-<arch>/`）不同，macOS 不按架构分目录，原因见 §5.3。查找顺序：环境变量 `NODU_STM32_TOOLKIT` → 安装包内的路径 → 开发环境的 `desktop/.tools/stm32/<platform>/`。开发环境的目录由新脚本 `scripts/build-toolkit.cjs` 生成，做法与 `build-media.cjs` 生成 `.tools/media` 相同。
- 工具包目录只读，Nodu 从不写入。编译产物、clangd 索引和备份分别放在工程目录和用户数据目录里。
- 调用工具时，子进程的 PATH 只包含工具包目录（[FUNCTIONAL-DESIGN §4.2](FUNCTIONAL-DESIGN.md#42-位置与查找)），学生电脑上装的其他 GCC 或 CMake 不会混进来。

## 5. 打包流水线

新脚本 `desktop/scripts/build-toolkit.cjs` 输出 `.tools/stm32/<platform>/`，由 `package-electron.cjs` 复制进安装包。输入只有 `toolkit.lock.json`（组件、版本、上游地址、上游 SHA-256、裁剪规则）和构建脚本，同样的输入得到同样的输出。

### 5.1 组件来源

| 组件 | macOS（arm64 / x64） | Windows x64 | 处理 |
| --- | --- | --- | --- |
| Arm GNU 14.2.Rel1 | 官方 darwin-arm64 / darwin-x86_64 归档（arm64 的 SHA-256 已在 P0 核对） | 官方 Windows 主机版（i686 还是 x86_64、zip 还是 exe，M1 核对） | 按 §3 规则裁剪；目标库和头文件只取一份，供各平台共用（§5.3） |
| CMake 4.4.3 | 官方 macOS 归档 | 官方 Windows zip | 去掉帮助文档与 GUI |
| Ninja 1.13.2 | 官方归档 | 官方 zip | 原样 |
| OpenOCD 0.12.0 | 从固定源码构建，带 libusb、hidapi | 在现有 Windows 构建机上用 MSYS2 构建（工作目录在 D 盘） | 保留 `share/openocd/scripts`；xPack 0.12.0-7 作为备选 |
| stm32flash 0.7 | 从固定源码构建（SHA-256 `c4c9cd8b…`） | 同左，MinGW | 原样 |
| clangd 23.1.0 | 官方 mac 包，拆成单架构并剥离符号 | 官方 windows 包 | 只保留 `clangd` 与内置头文件 |
| SDK CubeF4 1.28.3 / CubeF1 1.8.7 | 按 P0 锁定的 Cube、HAL、Device 三个 commit 取得 | 同左 | 按 §3 取子集，保留许可文件 |

### 5.2 步骤

1. 下载上游文件，核对上游公布的 SHA-256；没有公布摘要的，核对锁文件中第一次引入时记录的摘要。
2. 构建 OpenOCD 与 stm32flash。
3. 按裁剪规则复制文件；展开符号链接与硬链接；加入许可文件。
4. 冒烟测试：用工具包编译 3 个模板 × 2 颗芯片，BIN 摘要与上一次构建一致；OpenOCD、stm32flash、clangd 能输出版本号；clangd 能对模板工程给出补全。
5. 生成 `toolkit.json`：每个文件的相对路径、大小、SHA-256，以及组件版本与许可。
6. 检查最长路径。目前最长的相对路径为 77 个字符；Windows 默认安装位置加上这段路径约 210 个字符，在 260 字符的限制以内。超过 200 个字符时构建失败，必须先缩短。
7. 把 GPL 组件的对应源码、构建脚本和补丁打包，与安装包一起发布（§10）。

### 5.3 macOS：universal 合并与签名

现有打包流程先分别构建 arm64 和 x64 两个应用，再用 `@electron/universal` 合并。这个工具对两边同一路径的文件有固定规则（见 `node_modules/@electron/universal/dist/index.js`）：

- 两边内容不同的 Mach-O 文件用 `lipo` 合成双架构文件；
- 两边已经是双架构的 Mach-O 文件不处理；
- 其他普通文件两边必须逐字节相同，否则合并失败。

工具包据此放在**同一个路径** `resources/toolkits/stm32/darwin/`（不像现有侧车那样分成 `darwin-arm64/` 和 `darwin-x64/` 两个目录）。主机程序自动合成双架构，头文件、目标库、CMake 模块、OpenOCD 脚本、SDK 等共用文件只存一份。

Arm 的 darwin-arm64 与 darwin-x86_64 两个归档是分别构建的，其中的目标库（`.a`、`.o`）不保证逐字节相同。所以目标库和头文件只取 darwin-arm64 归档里的一份，两种架构都用它，流水线另外核对两份之间只有时间戳等元数据不同。这些是 Cortex-M 的目标代码，与电脑是哪种 CPU 无关。

按 §3 的测量估算：arm64 的主机程序 156.3 MB（zip 后 58.1 MB），共用文件 82.1 MB（zip 后 15.7 MB）；x64 主机程序按同等大小计。universal 安装包因此增加约 132 MB，安装后约 390 MB；单架构安装包增加约 74 MB，安装后约 240 MB。

签名：Apple Silicon 上未签名的 arm64 程序无法运行。现有流程只对 `.app` 做 ad-hoc 签名，`codesign --deep` 不会可靠地签到 `Resources` 里的普通可执行文件，所以打包脚本要先对工具包里的每个 Mach-O 文件单独签名，再签整个应用。有 Developer ID 后，二者一起改为正式签名并公证；公证要求每个可执行文件都启用 hardened runtime，届时需要验证 GCC、OpenOCD、clangd 在 hardened runtime 下能否正常运行（未验证）。

### 5.4 Windows

- 现有交付是便携 zip。zip 内的工具包按普通文件解压，不需要额外处理。
- 工具包里的 `.exe` 和 `.dll` 没有代码签名，杀毒软件可能误报或隔离（OpenOCD 这类直接操作 USB 的程序尤其容易被误报）。§6 的完整性检查能发现被隔离的文件，并在提示里说明可能的原因。
- 以后改为安装程序（NSIS 或 MSI）时，安装包按 LZMA 压缩，体积会小于 zip。

## 6. 首次使用与完整性检查

工具包随应用一起安装，不需要安装步骤。第一次打开 C 工程时：

1. 读取 `toolkit.json`，检查每个文件存在且大小正确。共约 3600 个文件，只看文件元数据，耗时应在 1 s 以内（未实测）。
2. 后台对全部文件做一次 SHA-256 校验（约 240 MB），结果记在用户数据目录。之后每次只做第 1 步。
3. 任何一步失败都不能编译，提示改为：`STM32 工具包有 3 个文件缺失或损坏。重新安装 Nodu 可以修复；如果反复出现，检查杀毒软件是否隔离了 Nodu 的文件。`“详情”中列出文件名。
4. 设置中的“检查工具包”随时重新执行第 2 步（效果图 03）。

**Windows 中文路径。** Nodu 安装在含中文的路径下时（例如用户名是中文，默认安装到 `C:\Users\张三\…`），工具包的路径也含中文。GCC、Ninja、OpenOCD 在 Windows 上处理非 ASCII 路径的情况未验证，M6 在中文用户名账户上实测：

- 实测没有问题：直接使用安装包内的工具包。
- 实测有问题：第一次使用时，把工具包复制到 `C:\Users\Public\Nodu\toolkits\<版本>\`（`%PUBLIC%`，路径为 ASCII，普通用户可写），校验后使用这份副本。复制约 240 MB 本地文件，提示 `正在准备 STM32 工具（只需一次）`。

学生工程本身的路径含中文时是另一个问题（PRD T6），同样在 M6 实测。

## 7. 版本与升级

- 每个 Nodu 版本内置**一个**工具包版本，记在 `toolkit.json`，新建工程时写入 `nodu.lock.json`。
- 0.2.x 的补丁版本不升级工具包；需要升级工具链时，随次版本发布，并在发布说明中列出组件变化。
- 打开工程时，若锁定的工具包版本与内置版本不同：显示一次提示 `这个工程用 STM32 工具包 2026.11.0 创建，当前 Nodu 自带 2027.05.0。编译结果可能略有不同。`，按钮为 `以当前版本编译` / `了解差异`。学生确认后更新锁文件；不确认时也照常用内置版本编译。0.2.1 不提供并存的旧版本（§11）。
- K210 的 MicroPython 工作流不使用工具包，不受版本变化影响。

## 8. 服务器：托管安装包

工具包打进安装包以后，服务器上只放 Nodu 安装包、校验值和 GPL 源码。不提供运行时的工具下载接口。

```
https://<下载域名>/nodu/<版本>/Nodu-<版本>-mac-universal.zip
https://<下载域名>/nodu/<版本>/Nodu-<版本>-win-x64.zip
https://<下载域名>/nodu/<版本>/SHA256SUMS
https://<下载域名>/nodu/<版本>/sources/        GPL 组件的对应源码、构建脚本与补丁（§10）
```

- **国内节点**：对象存储加 CDN，加速区域选“中国内地”。阿里云和腾讯云的文档都要求这种情况下的域名**先完成 ICP 备案**，因此需要一个已备案的域名（D7）。
- **备份节点**：GitHub Releases 放同样的文件，供海外用户使用，也在国内节点故障时使用。
- 文件按版本存放，发布后不再修改，CDN 可以长期缓存（`Cache-Control: public, max-age=31536000, immutable`）。CDN 必须支持 HTTP Range 请求，这样浏览器才能继续下载中断的大文件。发布流程在上传后从每个节点各下载一次，核对 SHA-256。
- 下载页同时给出 SHA-256。macOS 包另有代码签名可以核对（目前只是 ad-hoc 签名，见 §5.3）。
- **macOS 默认提供 universal 包**：Safari 在 Apple Silicon 上也报告 Intel 的用户代理，下载页无法可靠地判断 CPU 类型。单架构包作为可选下载。
- **课堂**：教师下载一次，用 U 盘或局域网共享拷给学生。安装包本身就是离线包，不需要另外的离线导入功能。

**费用估算。** 0.1.4 的 universal 包为 358.6 MB，加上工具包约 490 MB。按腾讯云 CDN 中国内地按流量计费的公开价格（0–2 TB 为 0.21 元/GB，页面更新于 2026-02-11），一个班 40 人各自下载约 20 GB，约 4 元；1000 次下载约 490 GB，约 103 元。另有对象存储的容量费和回源流量费，相比之下很小。阿里云的价格没有核对到（帮助页返回 404）。

## 9. 是否需要登录后下载（D8）

建议 0.2.1 **不需要登录**，理由如下：

| 考虑 | 说明 |
| --- | --- |
| 访问控制 | 安装包可以用 U 盘拷贝，登录拦不住传播，起不到访问控制的作用 |
| 费用与滥用 | 流量费很低（§8）。如果出现盗链刷流量，用 CDN 自带的防盗链（Referer 白名单、带过期时间的 URL 鉴权）、流量告警和封顶处理，不需要用户账号 |
| 个人信息 | 账号要收集手机号或邮箱，需要隐私政策、用户同意、存储与删除流程。按《个人信息保护法》，不满 14 周岁未成年人的个人信息属于敏感个人信息，处理需要监护人同意。Nodu 的用户包括学生，具体要求需要法务确认 |
| 课堂 | 40 人同时注册、收验证码、找回密码，会占用上课时间；机房可能没有外网 |
| 下载统计 | 从 CDN 日志统计下载量，不需要知道是谁下载的 |

需要账号的场景是 AI 教学：模型调用有费用，需要按人限额；课程进度和教师班级管理也要账号。建议账号与 AI 教学一起设计，工具和安装包的下载仍然不需要登录。

## 10. 许可与源码

| 组件 | 许可 | 分发要求 |
| --- | --- | --- |
| GCC、binutils、GDB | GPL-3.0（GCC 运行库带 GCC Runtime Library Exception） | 随二进制提供对应源码 |
| newlib | BSD 风格的多种许可 | 保留许可声明 |
| OpenOCD | GPL-2.0 | 提供对应源码 |
| libusb、libftdi（OpenOCD 依赖） | LGPL-2.1 | 提供源码；以动态库形式分发，用户可以替换 |

| stm32flash | GPL-2.0 | 提供对应源码 |
| CMake | BSD-3-Clause | 保留许可声明 |
| Ninja | Apache-2.0 | 保留许可与 NOTICE |
| clangd | Apache-2.0 with LLVM Exception | 保留许可声明 |
| STM32 HAL | BSD-3-Clause（`LICENSE.md` 文本） | 保留版权与许可声明 |
| CMSIS | Apache-2.0 | 保留许可与 NOTICE |

- 这些工具作为独立程序被 Nodu 调用，与 Nodu 的 MIT 代码是并列分发，不链接进 Nodu。
- 源码与安装包放在**同一个下载位置**（§8 的 `sources/`）。GPL-2.0 第 3 节和 GPL-3.0 第 6 节都认可“在提供二进制的同一位置提供同等的源码访问”这种方式。旧版本安装包仍在提供下载时，对应的源码也要保留。
- OpenOCD 自行构建时只启用 ST-LINK 需要的依赖（libusb），不需要的依赖不链接，可以减少要处理的许可。CMSIS-DAP 是否需要 hidapi，M1 决定。
- 许可文件放在 `resources/toolkits/stm32/<platform>/licenses/`，打包脚本像现在检查 ffmpeg 许可元数据那样，把它们列为必需输入，并汇总进 `THIRD-PARTY-NOTICES.md`。
- ST-LINK 的 Windows 驱动不打进安装包。ST 的驱动许可是否允许再分发没有核对，下载又要登录 my.ST，所以继续引导学生到 ST 官网安装（PRD T9）。
- 以上是工程上的整理，发布前需要法务确认。

## 11. 以后：按需下载（不在 0.2.1）

以下情况出现时，再加入从 Nodu 服务器按需下载组件包：

- 需要同时提供多个工具包版本（老工程锁定的旧版本）；
- 新增 F0、G0、F7 等系列的 SDK，全部打进安装包太大；
- 只做 K210 的用户较多，需要不含 STM32 工具包的精简安装包。

届时的设计要点：

1. 组件包使用 tar.xz（比 zip 小 50–60 %，§3），与安装包放在同一组节点上。
2. 清单的可信来源：应用发布时已知的版本，摘要随应用发布；之后新增的版本，使用服务器上带 Ed25519 签名的索引，公钥内置在应用中。镜像节点只是传输通道。
3. 客户端按 4 MiB 分块下载，每块对照清单校验；某个节点 30 s 没有数据就换到另一个节点，从断点继续；应用重启后也能接着下载。现有的 `nodu-resources` 只有 15 分钟的整体超时，不支持 Range 请求，需要扩展。
4. 客户端通过一个“来源解析”接口取得下载地址。现在返回固定地址；以后如果需要登录，服务端改为返回短时有效的 CDN 鉴权地址，客户端不需要改动。
